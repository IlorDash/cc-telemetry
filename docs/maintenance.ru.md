# Обслуживание сервера

Эта страница о том, что делать с работающим сервером: обновить его, проверить, сделать резервную
копию и восстановить данные, изменить настройки, остановить или удалить. Про неполадки — на
странице [«Решение проблем»](troubleshooting.md).

Все команды запускайте в папке `cc-telemetry` на ПК с сервером.

| Ваш сервер | Как запускать команды `docker compose ...` и `bash linux-server-tools/...` |
| --- | --- |
| Linux | Как есть. Добавьте `sudo`, если вы не в группе `docker` |
| Windows | Поставьте перед командой `wsl -d Ubuntu --`, из PowerShell (подставьте имя своего дистрибутива, если он не `Ubuntu`) |

---

## Проверка стека

```bash
docker compose ps
```

Все сервисы в состоянии `Up`, а `views-init` — `Exited (0)`. `views-init` — разовое задание,
которое создаёт таблицы и представления `cc.*`, поэтому оно и не должно работать постоянно.
`cc-refresh` запускается после него и раз в 5 минут перестраивает две небольшие таблицы (см.
[Пересоздание представлений](#пересоздание-представлений)); после каждого прохода в его логе
есть `refresh ok`.

Логи одного сервиса (`-f` — следить за ними, `--tail 100` — последние строки):

```bash
docker compose logs otel-collector
docker compose logs clickhouse
docker compose logs grafana
docker compose logs views-init
docker compose logs cc-refresh
```

Лог коллектора — первое место, куда стоит смотреть, если события не приходят; после запуска в нём
есть строка `Everything is ready`.

Повторный запуск серверного скрипта тоже работает как проверка: он никогда не пересоздаёт `.env` и
не удаляет данные. Он печатает `FAIL` для того, что сломано, и `WARN` для того, что лишь вызывает
подозрение.

Чтобы выполнить SQL без ввода пароля, передайте запрос в `ch.sh`. Пароль берётся из `.env` и не
печатается:

```bash
echo "SELECT event, count() FROM cc.events GROUP BY event" | bash linux-server-tools/ch.sh
```

```powershell
"SELECT event, count() FROM cc.events GROUP BY event" | wsl -d Ubuntu -- bash linux-server-tools/ch.sh
```

## Обновление сервера

Обновление переводит сервер на новую версию этого репозитория. Ваши данные лежат в томе
`clickhouse-data`, и обновление их не удаляет.

### Linux

Запустите в папке `cc-telemetry` с теми параметрами, которыми обычно пользуетесь:

```bash
bash setup-server.sh --update
```

!!! note "В первый раз выполните `git pull` сами"
    Версии скрипта, выпущенные до появления `--update`, этого параметра не знают. Один раз
    выполните `git pull`, дальше пользуйтесь `--update`.

Команда проходит такие шаги и останавливается на первой проблеме:

| Шаг | Что делает | Когда отказывается |
| --- | --- | --- |
| Проверки | Ищет `.env`, задаёт ClickHouse пробный вопрос и проверяет рабочее дерево git | Нет `.env` (папка ещё не настроенный сервер); ClickHouse не отвечает; в отслеживаемых файлах есть локальные изменения (`.env` и `backup/` в git игнорируются и не считаются) |
| Страховочная копия | Записывает каждую таблицу `otel.*` в `backup/pre-update-<дата>-<время>/` и рядом — число строк каждой таблицы. Прежние копии остаются | Свободного места меньше, чем несжатый размер данных (копия столько и занимает); при запасе меньше 1,5 раза выводится предупреждение. Также останавливается, если не удалось создать папку или копия не получилась |
| Код | Выполняет `git pull --ff-only`. Слияния и перебазирования не будет | Pull не удался (ветка разошлась, нет сети): на стеке ничего не изменилось. Без upstream-ветки или без репозитория git — только предупреждение, и скрипт продолжает с файлами как есть |
| Серверный скрипт | Снова запускает `setup-server.sh` из обновлённого файла с вашими остальными параметрами: запускает изменившиеся контейнеры, пересоздаёт представления `cc.*` (и докопирует в `cc.events_t` недостающие события), применяет срок хранения (TTL, см. [Место на диске и срок хранения](#место-на-диске-и-срок-хранения)), повторяет проверки. Если `otel-collector.yaml` или файл в `grafana/provisioning/` новее запущенного контейнера (сравниваются время файла и время старта контейнера, поэтому это работает и когда `git pull` выполнен до `--update`), этот сервис перезапускается; изменение `grafana/provisioning/` также делает так, что на старом сервере появляется папка `ru` с русскими копиями дашбордов. Файлы дашбордов Grafana перечитывает сама | Обычные ошибки установки, см. [страницу сервера](server.md#если-что-то-не-работает) |
| Проверка данных | Перед копией фиксирует границу — срок хранения минус один день назад (179 дней при 180) — и считает в каждой таблице строки моложе неё; после обновления считает их снова с той же границей. Более старые строки может удалить TTL срока хранения: скрипт только сообщает, сколько их | В таблице стало меньше строк моложе границы: баннер `FAIL` с папкой копии, код выхода 1 |

В случае успеха он печатает `update finished, no data lost` с папкой копии и командой отката.
Папки копий за вас не удаляются: старые папки `pre-update-*` удаляйте сами, когда они больше не
нужны. Если Docker работает через `sudo`, файлы копии принадлежат root.

Обновление также публикует порт `4318` и открывает его в брандмауэре на сервере в сети, так что
порт получит и более старый сервер.

!!! warning "Grafana на старом сервере"
    Если в `.env` есть `OTLP_BIND=0.0.0.0`, но нет `GRAFANA_BIND` (его записывала старая версия
    скрипта), обновление публикует на `0.0.0.0` и Grafana и печатает `WARN GRAFANA_BIND was
    missing and OTLP_BIND=0.0.0.0: Grafana is now published on 0.0.0.0, reachable from the LAN
    (it was local-only before) ...`. Чтобы оставить Grafana на этом ПК, задайте `GRAFANA_BIND=127.0.0.1`
    в `.env` и снова запустите `bash setup-server.sh` либо передайте `--local-only`, чтобы
    закрыть и порты OTLP. См. [страницу сервера](server.md#порты-и-доступ-на-linux).

### Windows

В Windows-скрипте нет `--update`. Скачайте новую версию и запустите скрипт ещё раз:

```powershell
git pull
powershell -ExecutionPolicy Bypass -File .\setup-server.ps1
```

Скрипт запускает изменившиеся контейнеры и пересоздаёт представления `cc.*`. TTL срока хранения у
существующих таблиц он не меняет: шаги вручную — в разделе [Изменение срока
хранения](#изменение-срока-хранения). Он перезапускает `otel-collector` или `grafana`, если
`otel-collector.yaml` или файл в `grafana/provisioning/` новее запущенного контейнера, так что
скачанные настройки применяются; файл, который только «тронули», стоит одного лишнего
перезапуска на несколько секунд. На сервере, настроенном до появления русских дашбордов, после
этого перезапуска Grafana показывает папку `ru` с их копиями. Чтобы перезапустить сервис самим
(с префиксом WSL, если Docker работает в WSL):

```bash
docker compose restart otel-collector grafana
```

Автоматической страховочной копии в Windows нет. Если она нужна, [сделайте копию
сами](#резервная-копия-и-восстановление) до `git pull`. Чтобы применить только изменение в
`clickhouse/views.sql`, весь скрипт не нужен:

```bash
docker compose run --rm views-init
```

Серверу, настроенному до появления хука сессий, нужно ещё раз выполнить
`setup-server.ps1 -EnableLan`, чтобы открыть порт `4318`.

### Откат

В конце вывода `--update` указан прежний коммит. Чтобы вернуться к нему:

```bash
git checkout <previous commit>
bash setup-server.sh
```

В Windows запускайте `setup-server.ps1` вместо `setup-server.sh`. Данные остаются в томе, поэтому
после отката восстанавливать ничего не нужно. После отката выполните `git checkout main`, чтобы у
следующего `--update` была ветка для pull (на отсоединённом `HEAD` ничего не скачивается).

## Резервная копия и восстановление

`linux-server-tools/backup.sh` выгружает каждую таблицу `otel.*` в файл `<table>.native` в папке
`backup` (формат ClickHouse Native). Таблицы и представления `cc.*` не выгружаются: их заново
строят из `otel.otel_logs` `views-init` и `cc-refresh`.

```bash
bash linux-server-tools/backup.sh dump              # otel.* tables -> backup/<table>.native
bash linux-server-tools/backup.sh restore           # appends rows: use on a fresh, empty stack
bash linux-server-tools/backup.sh restore <table>   # one table only
```

На Windows-сервере с Docker в WSL, из PowerShell:

```powershell
wsl -d Ubuntu -- bash linux-server-tools/backup.sh dump
```

`BACKUP_DIR=<папка>` перед командой выбирает другую папку для выгрузки и восстановления.
Относительный путь отсчитывается от папки `cc-telemetry`, а не от текущей папки:

```bash
BACKUP_DIR=backup/pre-update-<date>-<time> bash linux-server-tools/backup.sh restore otel_logs
```

Если Docker требует `sudo`, после него переменная теряется. Передайте её через `env`:

```bash
sudo env BACKUP_DIR=backup/pre-update-<date>-<time> bash linux-server-tools/backup.sh restore
```

!!! warning "Восстановление добавляет строки"
    `restore` дописывает выгруженные строки к тем, что уже есть в таблице. Запускайте его только
    для таблиц, которые сейчас пусты, например на новом стеке после `setup-server.*`. В таблице,
    где строки уже есть, получатся дубликаты. Сначала сверьте число строк.

!!! warning "В копии лежат ваши промпты"
    `backup/` исключена из git, потому что в выгрузке есть всё, что хранит стек, в том числе
    промпты. Храните её там же, где храните другие личные файлы. При Docker в WSL данные лежат
    внутри дистрибутива: `wsl --unregister` их удаляет, поэтому сначала сделайте копию.

Выгрузка в формате Native, поэтому она не привязана к тому. Чтобы перенести данные на сервер с
другой версией ClickHouse, восстановите их в новый стек и сверьте число строк каждой таблицы.

## Смена версии ClickHouse

По одну сторону границы 22.3 тег меняется на месте: `25.8` на `26.3` или `22.3.20.29` на другой
релиз 22.3. Между ClickHouse 22.3 (тег для Raspberry Pi 4) и более новой версией существующий том
данных не переживает смену: 25.x неверно читает индексы кусков, записанных версией 22.3
(дашборды падают с `CORRUPTED_DATA`), а том, записанный более новым ClickHouse, на 22.3 вообще не
запускается. Поэтому `setup-server.sh` такую смену **отказывается** делать, пока в томе есть данные
или пока ClickHouse не отвечает, а том существует, и останавливается до записи тега. Принудительного
флага нет. Перенесите данные через выгрузку:

1. Выгрузите данные в новую папку и убедитесь, что файлы не пустые:
   `BACKUP_DIR=backup/version-change-<date> bash linux-server-tools/backup.sh dump`
   (с `sudo`: `sudo env BACKUP_DIR=... bash ...`). При `--update` выгрузка обновления уже сделана;
   папка названа в сообщении об ошибке.
2. Остановите стек: `docker compose down`, **без** `-v`. Пока стек не запущен, клиенты не могут отправлять данные.
3. Удалите том ClickHouse, то есть данные, которые хранит выгрузка:
   `docker volume rm <project>_clickhouse-data` (точное имя есть в сообщении об ошибке, его
   показывает и `docker volume ls`).
4. Запустите с новой версией: `bash setup-server.sh --clickhouse-version <tag>` и ваши остальные параметры.
5. Восстановите: `BACKUP_DIR=backup/version-change-<date> bash linux-server-tools/backup.sh restore`.
   Восстановление идёт через материализованное представление, поэтому `cc.events_t` заполняется
   им же. Сверьте число строк таблиц с выгрузкой.

Если ClickHouse не отвечает, скрипт не может узнать, есть ли в томе данные, и тоже отказывается.
Том, которым никогда не пользовался работающий ClickHouse (например, контейнер не стартовал на
этом процессоре), данных не содержит: после `docker compose down` (без `-v`) удалите его
командой `docker volume rm` и запустите скрипт снова. Если вы вручную изменили
`CLICKHOUSE_VERSION` в `.env` и переходить не хотите, верните прежнее значение и запустите
скрипт снова.

На Windows-сервере с Docker в WSL выполняйте те же команды с `wsl -d Ubuntu --` в начале.
`setup-server.ps1` тег не записывает, поэтому в шаге 4 задайте `CLICKHOUSE_VERSION=<tag>` в `.env`
вручную и запустите `setup-server.ps1`. На Windows скрипт эту смену не проверяет, поэтому шаг 1
не пропускайте.

!!! warning "Сначала копия"
    Шаг 3 удаляет единственную копию данных на сервере. Делайте его, только проверив выгрузку.

## Пересоздание представлений

Коллектор записывает сырые события в `otel.otel_logs`. Дашборды читают представления `cc.*`,
которые не разбирают эти сырые события при каждом запросе:

- материализованное представление `cc.events_mv` раскладывает каждое новое событие Claude Code в
  таблицу `cc.events_t` сразу при поступлении;
- представления `cc.*` — обычные представления над этой таблицей и над двумя небольшими: проект
  каждой сессии (`cc.session_project_t`) и советы (`cc.tips_t`). Эти две таблицы раз в 5 минут
  перестраивает сервис `cc-refresh` по `clickhouse/refresh.sql`. Поэтому у новой сессии до 5 минут
  может быть проект `unknown`, а советы актуальны на момент последнего прохода.

Правка `clickhouse/views.sql` меняет то, что показывают дашборды, за всю историю. Примените её
так:

```bash
docker compose run --rm views-init
```

Команда ждёт, пока коллектор создаст `otel.otel_logs`, создаёт недостающие таблицы (`schema.sql`),
докопирует из `otel.otel_logs` события, которых ещё нет в `cc.events_t`, по месяцу за раз
(`backfill.sql`), и пересоздаёт представления. Её можно повторять. После первой установки или
обновления с большой историей копирование занимает время. То же делает запуск `setup-server.sh`
или `setup-server.ps1`. Если `views-init` завершается с ошибкой, `docker compose up -d` тоже
завершается с ошибкой, а серверные скрипты печатают его лог.

!!! note "Изменение `cc.events_mv` или колонок `cc.events_t`"
    `views-init` создаёт их через `CREATE ... IF NOT EXISTS`, поэтому на существующем сервере
    изменение пропускается, а сохранённые строки остаются со старыми значениями. Такому изменению
    нужен перенос: сначала копия, затем пересборка `cc.events_t` из `otel.otel_logs` по месяцу за
    раз (одна вставка больше чем за 100 дней отклоняется).

Не запускайте `clickhouse/refresh.sql` вручную, пока работает `cc-refresh`.

## Место на диске и срок хранения

Данные хранятся `RETENTION_DAYS` дней, это ключ в `.env`: TTL удаляет более старые строки из
таблиц `otel.*` и из `cc.events_t`, по целому дню за раз. `setup-server.sh` записывает ключ, если
его нет: 180 с ClickHouse 22.3 (Raspberry Pi 4, см. [страницу сервера](server.md#порты-и-доступ-на-linux)),
иначе 365. При следующих запусках значение сохраняется. `setup-server.ps1` его не записывает, а
без ключа стек использует 365.

Claude Code удаляет свои локальные файлы сессий примерно через 30 дней, поэтому сервер хранит
вашу историю дольше, чем ПК.

Сколько места занимают данные:

```bash
echo "SELECT table, formatReadableSize(sum(bytes_on_disk)) AS size, sum(rows) AS rows FROM system.parts WHERE database IN ('otel', 'cc') AND active GROUP BY table" | bash linux-server-tools/ch.sh
```

События хранятся дважды: сырыми в `otel.otel_logs` и разложенными в `cc.events_t`. Об удалении
данных — на странице [«Данные и приватность»](data.md#удаление-данных).

### Изменение срока хранения

Измените `RETENTION_DAYS` в `.env` и снова запустите серверный скрипт.

| Сервер | Что происходит |
| --- | --- |
| Linux | `setup-server.sh` меняет TTL существующих таблиц. Более долгий срок вопросов не требует. Более короткий удаляет строки старше нового срока: обычный запуск спрашивает в терминале (по умолчанию «нет»; `--yes` на этот вопрос не отвечает; без терминала шаг пропускается с предупреждением), `--update` продолжает после своей копии |
| Windows | `views-init` ставит TTL только на таблицы `otel.*`, у которых его нет и в которых нет строк старше срока. Существующий TTL меняйте сами (ниже) |

На Linux `setup-server.sh` также перечисляет старые таблицы системных журналов (`query_log`,
`text_log`, `trace_log`, `metric_log` и другие, [отключённые ниже](#ограничения-ресурсов-и-журналы),
вместе с ротированными копиями `query_log_0`, ...), оставшиеся от прежней установки: со строками,
размером и командой `DROP TABLE` для каждой, и общий размер; сам он их не удаляет. Если журнал
всё ещё пишется, работающий ClickHouse ещё не загрузил конфиг: выполните
`docker compose restart clickhouse` и запустите скрипт снова.

На Windows их никто не перечисляет. После перезапуска ClickHouse выведите таблицы и удалите
ненужные (`ch.sh` выполняется внутри WSL):

```powershell
"SELECT name, total_rows, formatReadableSize(total_bytes) AS size FROM system.tables WHERE database = 'system' AND match(name, '_log(_[0-9]+)?$') ORDER BY total_bytes DESC" | wsl -d Ubuntu -- bash linux-server-tools/ch.sh
"DROP TABLE system.text_log SYNC" | wsl -d Ubuntu -- bash linux-server-tools/ch.sh
```

В списке будут и таблицы журналов, которые вы включили сами, и пустые.

Чтобы изменить его вручную, выполните SQL через `ch.sh` (замените `180`; если срок сокращается,
сначала сделайте копию):

```sql
ALTER TABLE cc.events_t MODIFY TTL toDateTime(ts) + INTERVAL 180 DAY;
ALTER TABLE otel.otel_logs MODIFY TTL TimestampTime + toIntervalDay(180);
ALTER TABLE otel.otel_metrics_sum MODIFY TTL toDateTime(TimeUnix) + toIntervalDay(180);  -- также _gauge, _histogram, _exponential_histogram, _summary
```

## Ограничения ресурсов и журналы

`CLICKHOUSE_LIMITS=small` в `.env` запускает ClickHouse с ограничениями для небольшого сервера,
например Raspberry Pi 4: 3 ГБ памяти на сервер и 1,5 ГБ на запрос, 3 потока на запрос, два
фоновых слияния, небольшие кэши и не больше 8 запросов одновременно. `CLICKHOUSE_CPUS` ограничивает
контейнер этим числом ядер (`0` — без ограничения). `setup-server.sh` записывает `small` и `2` с
ClickHouse 22.3, иначе `none` и `0`; без ключей стек использует `none` и `0`, то есть настройки
ClickHouse по умолчанию. Ограничения лежат в `clickhouse/limits/small/`. Запрос дашборда, которому
нужно больше 1,5 ГБ, завершается с ошибкой, а не замедляет сервер.

На любом сервере ClickHouse не пишет системные журналы (`query_log`, `processors_profile_log`,
`error_log`, `trace_log` и остальные, которые версия ClickHouse включает по умолчанию), а его
текстовый лог ограничен уровнем `warning`, 10 МБ на файл и двумя старыми файлами
(`clickhouse/config.d/common.xml` и `clickhouse/users.d/common.xml`). Коллектор записывает
события в ClickHouse раз в 30 секунд, поэтому новое событие попадает в дашборды с задержкой до
30 секунд.

После правки одного из этих XML-файлов выполните `docker compose restart clickhouse`. Изменению
`CLICKHOUSE_LIMITS` или `CLICKHOUSE_CPUS` нужен `bash setup-server.sh` или `docker compose up -d`:
контейнер `clickhouse` пересоздаётся за несколько секунд, коллектор пока повторяет попытки.

!!! tip "Как найти медленную панель"
    Включите `query_log` на время: удалите строку `<query_log remove="1"/>` в
    `clickhouse/config.d/common.xml`, задайте `<log_queries>1</log_queries>` в
    `clickhouse/users.d/common.xml` и выполните `docker compose restart clickhouse`. Медленный
    запрос будет в `system.query_log` (`query_duration_ms`, `query`). Потом верните оба файла,
    снова перезапустите ClickHouse и выполните `DROP TABLE system.query_log SYNC`.

## Изменение настроек

| Вы хотите | Сделайте так |
| --- | --- |
| Другой порт Grafana (Linux) | `bash setup-server.sh --grafana-port 3001`. Порт сохраняется как `GRAFANA_PORT` в `.env` |
| Другой порт Grafana (Windows) | Не поддерживается: скрипт проверяет и печатает только порт `3000` |
| Другие порты OTLP | Не поддерживается: `4317` и `4318` зафиксированы |
| Оставить сервер только на этом ПК или открыть его для сети (Linux) | `bash setup-server.sh --local-only` или `--lan`. Чтобы изменить только Grafana, задайте `GRAFANA_BIND` в `.env` (`127.0.0.1` или `0.0.0.0`) и снова запустите скрипт: он сохранит значение. См. [страницу сервера](server.md#порты-и-доступ-на-linux) |
| Открыть сервер для сети (Windows) | `setup-server.ps1 -EnableLan` |
| Хранить данные другой срок | Задайте `RETENTION_DAYS` в `.env` и запустите серверный скрипт, см. [Изменение срока хранения](#изменение-срока-хранения) |
| Включить или выключить ограничения небольшого сервера | Задайте `CLICKHOUSE_LIMITS` (`small` или `none`) и `CLICKHOUSE_CPUS` в `.env` и запустите серверный скрипт, см. [Ограничения ресурсов и журналы](#ограничения-ресурсов-и-журналы) |
| Другая версия ClickHouse (Linux) | `bash setup-server.sh --clickhouse-version <tag>`. Смена между 22.3 и более новой версией отклоняется, пока есть данные: см. [Смена версии ClickHouse](#смена-версии-clickhouse) |
| Сменить пароль администратора Grafana | Для этого в репозитории нет параметра. Grafana читает `GRAFANA_ADMIN_PASSWORD` из `.env` при создании своей базы при первом запуске, поэтому правка `.env` позже пароль не меняет. Смените его в самой Grafana (ваш профиль) или сбросьте командой `grafana cli admin reset-admin-password` внутри контейнера grafana |
| Сменить пароль ClickHouse | Для этого в репозитории нет параметра. `CLICKHOUSE_PASSWORD` из `.env` применяется только при первом создании тома ClickHouse, а коллектор, Grafana и `ch.sh` читают его из `.env`. Если сменить его позже, соединение сломается |

## Остановка и удаление стека

| Вы хотите | Команда | Ваши данные |
| --- | --- | --- |
| Остановить стек | `docker compose stop` | Сохраняются |
| Запустить снова | `docker compose up -d` или серверный скрипт | Сохраняются |
| Остановить и удалить контейнеры | `docker compose down` | Остаются в томах `clickhouse-data` и `grafana-data` |
| Удалить всё, включая данные | `docker compose down -v` | **Удаляются** |

!!! warning "`down -v` удаляет все собранные данные"
    `-v` удаляет тома, а вместе с ними все события, которые сохранил стек, и собственную базу
    Grafana. Отменить это нельзя. Сначала сделайте копию (см. [Резервная копия и
    восстановление](#резервная-копия-и-восстановление)) и убедитесь, что она не пустая. Обычный
    `docker compose down` безопасен.

На Windows-сервере с Docker в WSL данные удаляет и `wsl --unregister <дистрибутив>`.

Остановка стека не отменяет того, что настроил Windows-скрипт. Уберите это сами, когда оно
больше не нужно:

| Что | Как убрать |
| --- | --- |
| Keepalive (только WSL) | Удалите `cc-telemetry-keepalive.vbs` из папки автозагрузки; процесс завершится при следующем выходе из системы или перезагрузке |
| Правила брандмауэра и переадресации портов (`-EnableLan`) | Правила `OTLP 4317 (Claude Code telemetry)` и `OTLP 4318 (Claude Code telemetry)` и переадресации `netsh interface portproxy` для обоих портов. Нужны права администратора |
| Правила брандмауэра в Linux | `ufw delete allow <port>/tcp` или `firewall-cmd --remove-port=<port>/tcp` |

Клиенты продолжают слать данные на сервер, пока вы не [отмените их настройки](clients.md#отмена).
